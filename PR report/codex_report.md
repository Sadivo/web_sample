# 航港大數據創意應用競賽報告書審查報告

**審查對象**：`6. 賽前報告/航港大數據創意應用競賽報告書v3.docx`  
**審查日期**：2026-05-25  
**審查版本**：v3 更新版  
**審查重點**：確認 v3 相對 v2 的修正狀況，並標示仍會被評審直接挑出的風險點

## 結論

v3 相較 v2 有明顯進步，最重要的是幾個關鍵詞與數字已經收斂，包含：

- 作品名稱已統一為 `OceanAI`
- `Phycial AI` 已修正為 `Physical AI`
- API 端點數量已修正為 `12 個`
- 第八章已補入參考文獻，不再空白

但這份 v3 仍然不適合直接送審。原因不是內容不夠，而是還有幾個會直接影響專業感與可信度的問題沒有處理完，尤其是第五章雖然更新過，但反而把「概念包裝」拉得更滿，與現有 `api/` 實作的落差仍然很大。

目前最需要先處理的點是：

1. 封面隊伍名稱仍是垃圾測試文字
2. 封面日期仍顯示 `115 年 6 月`
3. 摘要仍未形成可獨立閱讀的完整段落
4. 第五章更新後仍以 `OpenClaw`、多模型推論與數位雙生敘事為主，和實際 FastAPI 實作不對齊
5. `iMarine` 仍未被寫成核心資料源或校正來源
6. 參考文獻雖已補入，但格式仍不完整，缺 URL、存取日期與一致格式
7. 第二章標題仍寫「三大結構性挑戰」，但內文實際列出四個子節

## 一、P0：必修項目

### 1. 封面隊伍名稱仍是測試垃圾文字

位置：

- 封面第 2 行「參賽隊伍」

現況：

- `南港展覽館館長掌管官方觀光網站綻放萬丈光芒Computex黃仁勳難波萬`

問題：

- 這不是正式隊名。
- 這會讓整份報告看起來像尚未清稿的測試檔。
- 若依競賽規定需匿名，這一行更應直接移除。

建議：

- 若要匿名提交，直接刪掉這一整行。
- 若大會允許隊名顯示，請改成正式隊名，且全文一致。

### 2. 封面日期仍是 `115 年 6 月`

位置：

- 封面日期行

現況：

- `中 華 民 國  115 年  6 月`

問題：

- 若這份是最終送件版，日期與目前繳交時點不一致。
- 即使是內部版本，也容易讓評審覺得文件版本管理不嚴謹。

建議：

- 若是正式交件版，請改成實際送件月份。
- 若這是內部工作稿，請另存為草稿版本，不要直接輸出成最終 PDF。

## 二、P1：高優先修正

### 3. 摘要仍未形成完整正文

現況：

- 目錄有「摘要」
- 但正文閱讀起來仍像是直接進入研究主軸，摘要沒有形成可獨立閱讀的完整段落

問題：

- 競賽書面報告需要一段可獨立閱讀的摘要，否則開頭說服力不夠。
- 如果摘要只是短句或半成品，評審會直接把它視為排版未完成。

建議摘要應包含：

1. 背景與問題
2. 作品目標
3. 資料來源
4. 核心方法
5. 已完成成果
6. 預期效益

### 4. 第五章雖然更新，但與實作脫節問題仍在，而且更明顯

位置：

- 第五章「研究流程、推論邏輯與理論依據」

現況：

- v3 已經把這一章寫得比 v2 更完整，加入了更多方法論與架構描述。
- 但內容仍大量使用 `OpenClaw`、`Layer 1~5`、`智慧雙燃料航運數位雙生系統`、`雙半球架構` 等敘事。
- 文中還延伸到 `RoBERTa`、`LLM`、`PINN`、`XGBoost`、`PPO`、`NSGA-II` 等多種模型與最佳化敘事。

問題：

- 這些內容與目前 repo 內已完成的 `FastAPI routers/services` 並不一致。
- 現有實作核心是風險資料整合與查詢 API，不是完整的雙燃料數位雙生系統。
- v3 的第五章比 v2 更像研究提案或產品藍圖，而不是已完成作品的實作說明。
- 如果評審追問 Demo、API、資料流或模組對照，這一章會直接暴露落差。

建議二選一：

1. 保留這章，但明確標註為「未來規劃藍圖」
2. 直接改寫成「現有 MVP 的資料流、ETL、API 與風險分數推論流程」

我建議第二種，因為比較符合目前已實作內容，也比較能被評審驗證。

### 5. `iMarine` 仍然沒有被寫成核心資料源

位置：

- 第 2 章批判現有工具的段落
- 第 8 章參考文獻

現況：

- `iMarine` 在正文中仍偏向被提及為背景或批判對象。
- 沒有在資料方法章節中清楚描述「系統如何實際使用 iMarine」。

問題：

- 競賽配分中 `iMarine` 使用是獨立評分項目。
- 現在這份報告仍然會讓人覺得你們在用外部 API，而不是在強調 iMarine 的資料價值。

建議：

- 在第四章或第五章補一段「iMarine 數據整合與互補應用」
- 明確列出 iMarine 被用在哪些模型參數、基準值或驗證項目
- 至少把以下幾類資料寫進正文：
  - WBP 世界燃油價格
  - 四大港吞吐量
  - 24 小時泊靠時間分析
  - 進出臺灣各國際商港船舶
  - GSCPI 或其他航運指數

### 6. 參考文獻已補齊，但格式仍不夠完整

現況：

- 第八章已經不是空白，這點是進步。
- 但條目仍多為純文字列舉，缺少 URL、存取日期與一致格式。

問題：

- 形式上有文獻，但學術性與可追溯性不足。
- 若評審想查來源，會發現很多條目不好追。

建議：

- 每筆文獻補上 URL 或存取日期
- 中英文格式統一
- 政策、資料源、案例文獻分開列

### 7. 第二章標題與子節數量不一致

位置：

- `一、台灣航運現況：產業重要性與三大結構性挑戰`

現況：

- 內文實際上列出 4 個子節：
  - 戰略重要性
  - 綠色合規
  - 資源孤立
  - 缺乏主動預測能力

問題：

- 標題說三大，但內容是四段。
- 這是很容易被抓到的章節邏輯問題。

建議：

- 把標題改成「航運產業的結構性挑戰與戰略重要性」
- 或把第一段改成背景說明，後三段保留為三大挑戰

## 三、P2：中優先修正

### 8. `iMarine` 的寫法仍偏弱

雖然 v3 已經出現 `iMarine`，但目前仍沒有形成「本系統積極使用 iMarine」的敘事重心。

建議改成：

- `iMarine` 是本系統的基準校正資料源
- 外部即時 API 是補強來源
- 兩者並行，形成資料層與即時層的互補架構

### 9. 案例段落仍需要更明確的引用

第七章的 Maersk、Orca AI、紅海危機、巴拿馬運河案例有助於提升說服力，但目前仍偏敘述型，引用支撐不夠完整。

建議：

- 每個案例至少標示一個可查來源
- 數字要避免過度精確但無來源

### 10. 文字仍偏長，像提案書，不像正式報告

雖然 v3 比 v2 更一致，但很多段落仍然是長句堆疊、名詞密度過高。

建議：

- 每章都維持「問題 -> 方法 -> 現況 -> 效益」的結構
- 減少過度抽象的詞，例如：
  - `雙半球架構`
  - `全局重新規劃`
  - `智慧雙燃料數位雙生系統`

不是不能用，而是要有清楚定義，否則會顯得浮誇。

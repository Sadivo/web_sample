# 航港大數據創意應用競賽報告書審查報告

審查日期：2026-05-25  
審查對象：`6. 賽前報告/航港大數據創意應用競賽報告書.docx`

## 結論

這份報告的主題方向是對的，敘事也有完整性，但目前還不能直接送審。主要問題不是「內容不足」，而是「封面錯誤、命名不一致、實作與文字不對齊、引用缺失、草稿痕跡未清」。

如果要以評審角度看，最容易被扣分的不是技術深度，而是專業度與可信度。

## 一、優先級判定

### P0：必修，否則不建議送件

1. 封面隊伍名稱是明顯的臨時文字，必須改正。
2. 作品名稱在封面與內文不一致，必須統一。
3. `捌、參考文獻` 目前實質上是空的，必須補齊。
4. 報告中有多處與目前實作不一致的敘述，必須修正或降格為「規劃中」。

### P1：高優先，會直接影響專業感

1. 全文要清除草稿痕跡、問號占位、錯字與不正式語氣。
2. 摘要看起來不完整，需補成可獨立閱讀的正式摘要。
3. 第五章內容過度概念化，與目前 repo 實作落差過大。

### P2：建議修整，會提升得分穩定性

1. 數據與案例中的所有精確數字要補來源。
2. 章節標題與小節層級要統一。
3. 圖目錄、表目錄要重新更新。

## 二、具體問題與修改建議

### 1. 封面資訊錯誤

問題：

- 封面「參賽隊伍」欄位是臨時/亂碼式文字，不像正式隊名。
- 封面作品名是 `OceanAI - 航港智慧助手`，但正文大量使用 `GreenRoute AI`，命名不一致。

建議：

- 封面隊伍名稱改為正式隊名，若競賽要求匿名，則改成規定格式。
- 作品名稱統一成一個版本，全文都要一致。
- 封面日期與中華民國年、月格式再檢查一次，避免格式不一致。

### 2. 摘要不足

問題：

- 目錄中有「摘要」，但正文抽取後未看到完整可獨立閱讀的摘要段落。

建議摘要內容至少包含：

1. 問題背景
2. 作品目標
3. 資料來源
4. 核心方法
5. 目前完成度
6. 預期效益

建議字數：

- 200 到 350 字，單段或兩段即可。

### 3. 參考文獻缺失

問題：

- `捌、參考文獻` 目前沒有實際條目。
- 內文有大量數字與案例，但缺少來源會讓評審質疑可信度。

建議：

- 至少補上三類文獻：
  1. 政策與法規來源：IMO、EU ETS、FuelEU Maritime、CII/EEXI
  2. 資料源文件：iMarine、CWA、IMF PortWatch、OFAC、NGA、USCG、JTWC
  3. 案例與論文：Maersk、Orca AI、紅海危機、巴拿馬旱災等

### 4. 與實作不一致

問題：

- 第四章與第五章中，有些內容看起來已經實作完成，但實際 repo 並沒有這些模組。
- 例如：
  - `OpenClaw`
  - `orchestrator.pystate_memory.py`
  - `ais_ingestion.py`
  - `data_adapter.py`
  - `cost_calculator.py`
  - `emissions.py`

這些名稱不在目前 `api/` 實作內，容易被視為誇大或未落地。

建議：

- 若這些只是未來規劃，請明確標註為「未來延伸架構」。
- 若是要描述目前實作，請改寫成實際存在的架構：
  - `FastAPI routers/services`
  - `Open-Meteo / CWA / IOTH / NDBC / IMF PortWatch / OFAC / JCG / NGA / MND / USCG`
  - `risk_score`、`constraint`、`geo`、`weather`、`ocean`

### 5. 端點數量與現況不一致

問題：

- 報告寫「11 個 API 端點全數通過測試」。
- 但專案現況文件已記錄 12 個已驗證端點。

建議：

- 數字統一到目前最新實作狀態。
- 若報告內只想寫核心端點，可以改成：
  - 「核心風險 API 已完成並通過測試」
  - 再列出主要端點，不必強調固定數字，避免版本差異造成衝突。

### 6. 內容過度誇張，像提案稿，不像競賽成果報告

問題段落特徵：

- 使用大量高密度名詞堆疊
- 出現很多未證實的專有名詞
- 句子長、抽象、像簡報講稿，不像可送審書面報告

建議：

- 砍掉或縮短過度包裝的段落。
- 改成「問題 → 方法 → 目前成果 → 效益」四段式。
- 減少空泛名詞，例如：
  - `OpenClaw`
  - `雙半球架構`
  - `數位雙生系統`
  - `全局自適應最佳化`

不是不能用，而是要在正文裡有明確定義和對應實作，否則會顯得浮誇。

### 7. 錯字與草稿痕跡很多

已發現的明顯問題：

- `Phycial AI` 應改為 `Physical AI`
- `技術率竟` 應改為 `技術佐證` 或 `技術可行性`
- `所開發知系統` 應改為 `所開發之系統`
- `一直數據` 應改為 `即時數據`
- 目錄中與章節標題附近仍留有 `(?)`

建議：

- 整篇做一次全文校對。
- 先修正所有拼字、全形半形、英文大小寫、符號格式。
- 刪除草稿標記、測試語句與未定稿語氣。

### 8. 研究流程與理論依據過於超展開

問題：

- 第五章開始大量使用物理、運籌、微服務、DDD、ABM 等內容，但與目前實際 API 產品沒有清楚對應。
- 這會讓評審覺得你們「講得很大，但落地證據不足」。

建議：

- 把第五章收斂成：
  1. 資料流
  2. ETL 流程
  3. API 服務層
  4. Feature / Constraint / Risk 的推論邏輯
  5. 人機協作的預留機制

如果要談理論依據，建議只保留和實作真正有關的部分，不要把太多未實作的系統工程名詞塞進正文。

## 三、逐章修改方向

### 壹、研究主軸與目的

建議保留，但要更精簡。

要補強的點：

- 研究問題要更明確
- 目標要和目前已完成 API 對齊
- 不要把未完成的 Agent 功能寫成已上線

### 貳、創新性說明

這一章是目前最接近可用的，但仍要修兩件事：

1. 把創新性拆成「已完成」與「未來擴充」
2. 把雙層架構和現有 `api/` 實作對應清楚

建議明確寫成：

- 產品一：已完成的風險資料整合 API
- 產品二：規劃中的智慧決策層
- HIL：預留的回饋機制

### 參、現況分析

內容量足夠，但太長、太散。

建議改成三個重點：

1. 航運產業的風險痛點
2. 目前工具的不足
3. 你的系統如何補位

### 肆、資料分析模式與方法

這章需要明顯收斂。

建議改成：

- 資料來源清單
- 資料處理方式
- 特徵工程方法
- API 輸出格式
- 驗證方式

不要把還沒做完的模型架構寫成確定已完成。

### 伍、研究流程、推論邏輯與理論依據

這章最危險。

建議：

- 刪掉過度抽象的系統名詞
- 改成流程圖式敘述
- 用實際資料流與 API 鏈路說明

如果保留公式，只保留和專案現況直接相關的公式，例如：

- 風險分數加權
- 壅塞指數
- 海象風險門檻

### 陸、未來資料之應用

這章可以保留，因為它本來就適合講未來擴充。

建議把語氣改得保守一點：

- 由「已經能」改成「未來可」
- 由「系統會」改成「可擴充為」

### 柒、實際案例或國外文獻

這章要補引用，不然會變成純敘述。

建議至少加入：

- Maersk 數位轉型案例
- Orca AI 或其他航海 AI 案例
- 紅海危機案例
- 巴拿馬運河旱災案例

每個案例都要清楚標示來源。

- 這些 API 解決什麼問題

- 目前驗證到什麼程度
- 哪些是已完成、哪些是規劃中

不要把未完成的功能寫成既成事實。
